# Сопоставление деклараций и регуляций ТН ВЭД

Ранжирование регуляций по тексту таможенной декларации: для каждой декларации возвращаются
десять регуляций в порядке убывания релевантности.

## Установка

Среда готовится заранее, в лимит запуска не входит. **Нужен Python 3.10 или новее**
(код использует синтаксис `X | None`), проверялось на 3.11.

```bash
./prepare_env.sh
# если python в системе старее 3.10, укажите интерпретатор явно:
PYTHON=python3.11 ./prepare_env.sh
```

Скрипт проверяет версию Python, создает `.venv`, ставит зависимости из `requirements.txt`
и выкачивает две модели в `./models` по зафиксированным ревизиям. После этого сеть не нужна.

Вручную то же самое:

```bash
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python download_models.py --out ./models
```

## Запуск

```bash
python run.py --data ./data --out ./out
```

Пишет `out/predictions.csv` с колонками `declaration_id, rank, regulation_id, score`.
Запуск полностью офлайн: модели читаются из `./models` с `local_files_only=True`,
переменные окружения вроде HF_HUB_OFFLINE не требуются.

Быстрые проверки без моделей - контракт формата, нормализация, числовые
пороги, отрицания, тарифная квота:

```bash
python dev/selftest.py
```

Качество на размеченном dev-подмножестве:

```bash
python dev/evaluate.py --errors
```

## Результат

На размеченном вручную подмножестве из 62 деклараций (половина выданных данных):

| Конфигурация | P@1 | MRR@10 | Recall@10 |
|---|---|---|---|
| BM25 | 0,452 | 0,633 | 0,935 |
| плотный поиск bge-m3 | 0,565 | 0,713 | 0,968 |
| слияние RRF | 0,613 | 0,754 | 0,984 |
| + cross-encoder по 30 кандидатам | 0,597 | 0,766 | 1,000 |
| + атрибутный слой | 0,694 | 0,828 | 1,000 |
| + слой отрицаний | 0,710 | 0,840 | 1,000 |
| + приор от порядка слияния | **0,774** | **0,872** | **1,000** |

Recall@10 равен единице: верная регуляция всегда в выдаче, вся борьба идет за первое место.

Полный прогон 120 деклараций: ~10 минут на MacBook M1 (8 ГБ, MPS), пик памяти ~4,3 ГБ.
Укладывается в лимит 30 минут и 8 ГБ. Разбор ошибок - в `notes/error_analysis.md`.

Прошу обратить внимание на четвертую строку: cross-encoder сам по себе слегка **ухудшает** P@1
относительно слияния, хотя поднимает MRR и доводит Recall@10 до единицы. Он переупорядочивает
верхушку не всегда в лучшую сторону, потому что читает 384 токена и ловится на поверхностном
совпадении формулировок. Порядок слияния несет дополнительный сигнал, поэтому он возвращен
в итоговую сумму как приор - см. раздел про компромиссы.

## Подход

Пять ступеней, каждая закрывает свой тип ошибок.

**1. Нормализация** (`src/normalize.py`). Декларации записаны капсом, регуляции - обычным
регистром. Все приводится к нижнему регистру через NFKC, `ё` заменяется на `е`, десятичная
запятая на точку, тире всех видов на дефис. Отдельно чинится дефект выгрузки: в
`regulations.jsonl` потеряны надстрочные степени, `см?` вместо `см3` и `г/м?` вместо `г/м2`.

**2. Отбор кандидатов** (`src/lexical.py`, `src/dense.py`). Гибрид BM25 и плотного поиска
`BAAI/bge-m3`, слияние через Reciprocal Rank Fusion. BM25 написан на numpy: корпус из 360
документов не оправдывает внешнюю зависимость. Русская морфология ломает точное совпадение
токенов, поэтому применяется усекающий стеммер до 5 символов. Шкалы BM25 и косинуса
несопоставимы напрямую, ранги - сопоставимы, поэтому именно RRF, а не взвешенная сумма.
На выход идут 30 кандидатов.

**3. Переранжирование** (`src/rerank.py`). Cross-encoder `BAAI/bge-reranker-v2-m3` на парах
(декларация, регуляция). Bi-encoder укладывает "более 1000 см3" и "не более 1000 см3"
почти в одну точку, cross-encoder видит обе фразы одновременно - за счет этого Recall@10
доходит до единицы и растет MRR.

**4. Атрибутный слой** (`src/attributes.py`). Из описания регуляции разбираются числовые
пороги, из декларации - измеренные значения; нарушение порога штрафуется. Подробности ниже.

**5. Слой отрицаний** (`src/negation.py`). Штраф за признак, который декларация отрицает,
а регуляция утверждает. Подробности ниже.

### Атрибутный слой

Ключевое наблюдение: в выданных данных на каждую декларацию приходится один верный код и
два соседа по той же субпозиции, а различаются они не смыслом, а атрибутами. 105 из 360
регуляций содержат числовой порог. Примеры троек:

| Декларация | Кандидаты | Различитель |
|---|---|---|
| Газойль, сера 0,12 мас.% | 2710194290 / 2710194600 / 2710194800 | не более 0,05 / 0,05-0,2 / более 0,2 |
| Тягач, возраст 6 лет | 8701229011 / 8701229012 / 8701229019 | более 7 / 5-7 / не более 5 лет |
| Доска, сечение 32x140 мм | 4407199205 / 4407199206 / 4407199209 | не менее 100 мм / более 6 мм |

Слой работает так:

- из описания регуляции извлекаются тройки (атрибут, оператор, значение): операторы
  `более / не более / менее / не менее / свыше / превышающей`, конструкция
  `более X, но не более Y` распознается как продолжение того же атрибута;
- из декларации извлекаются измеренные значения тех же атрибутов;
- атрибут определяется по **ближайшему** к числу ключевому слову, а не по первому
  подходящему: иначе `сера 0,12 мас.%` в начале строки притягивает `плотность 842 кг/м3`
  в конце;
- у каждой единицы измерения есть класс (масса, объем, длина, доля массовая, доля объемная,
  время, мощность). Атрибут применим только к своему классу. Это отсекает мусор вроде
  `возраст = 265 кВт` и, что важнее, разводит `мас.%` и `об.%`: для концентрата колы
  с сахарозой 12 мас.% и спиртом 0,10 об.% без такого разделения сахароза удовлетворяла бы
  порог "более 0,5 об.% спирта";
- длины приводятся друг к другу (мм/см/м), бесразмерное `%` в декларации сопоставляется
  и с `мас.%`, и с `об.%`;
- `сечение 32 x 140 мм` разбирается в толщину 32 и ширину 140 (меньшая сторона - толщина);
- **возраст выводится из года выпуска**: регуляции оперируют формулировкой "с момента
  выпуска которых прошло более 5 лет", а декларация часто содержит только "год выпуска
  2023". Год подачи берется из номера декларации `ND` (формат `.../ДДММГГ/...`), а не
  зашивается константой;
- выполненный порог дает бонус, нарушенный - втрое больший штраф, отсутствие атрибута
  в декларации нейтрально. Асимметрия намеренная: нарушение порога это надежный сигнал
  "точно не сюда", а совпадение - слабый, потому что порогу удовлетворяют и соседи.

Отдельным правилом обрабатывается **тарифная квота**. Ввоз в рамках квоты классифицируется
по подсубпозиции со ссылкой "в порядке, указанном в дополнительном примечании ЕАЭС",
вне квоты - по общей. Правило двустороннее: "в рамках тарифной квоты" премирует кандидата
со ссылкой на дополнительное примечание, "вне тарифной квоты" - штрафует. В выданных данных
это 6 регуляций и 4 декларации, поровну в обе стороны.

### Слой отрицаний

Cross-encoder систематически ошибается на отрицаниях: видит слово "производственный"
и в декларации, и в кандидате, принимает это за совпадение и не замечает частицы "не".

| Декларация | Ошибочно выбирался | Верно |
|---|---|---|
| комбинезон, **не является** производственной спецодеждой | комбинезоны **производственные** | прочие комбинезоны |
| плеер, цифровой дисплей **отсутствует** | плееры с аналоговой и **цифровой** системой | плееры прочие |
| лента, текстильное армирование **отсутствует** | армированные **текстильными** материалами | армированные металлом |

Текст с обеих сторон делится на области отрицания и утверждения, затем начисляется штраф
за основы, которые декларация отрицает, а регуляция утверждает. Учитываются три
конструкции:

- **префиксная** - отрицаемое справа: "не является спецодеждой", "без футеровки";
- **постфиксная** - отрицаемое слева: "армирование отсутствует", "биодизель не содержит".
  Признак этой конструкции - глагол в конце клаузы. Различать позицию обязательно: в
  "биодизель **не содержит**" объект стоит слева, а в "**не содержащие** биодизель" - справа;
- **слитная** - "несеменной" отрицает "семенной".

Полярность считается симметрично для декларации и регуляции. Это важно: декларация
"биодизель не содержит" и регуляция "не содержащие биодизель" согласуются, а не
конфликтуют, потому что термин отрицается с обеих сторон.

### Справочник ТН ВЭД

`src/tnved_tree.py` разбирает `tnved_knowledge.txt` (21 тыс. узлов) и раскрывает ссылки
между позициями. Часть регуляций описана через отсылку: "части и принадлежности музыкальных
инструментов товарной позиции 9205". Что такое 9205, известно только из справочника -
это духовые инструменты, в том числе кларнеты. Раскрытие ссылки делает декларацию про
мундштук кларнета сопоставимой с этой регуляцией.

Исключающие ссылки не раскрываются: в "лекарственные средства (кроме товаров товарной
позиции 3002, 3005 или 3006)" подстановка описаний 3002/3005/3006 добавила бы в документ
текст ровно про то, чем товар **не** является.

Раскрытые ссылки идут только в cross-encoder и **не** идут в BM25 и плотный поиск:
в мешке слов они размывают документ и на dev роняют P@1 с 0,406 до 0,344.

## Рассмотренные альтернативы

**Локальная LLM как судья поверх топ-5.** Отклонено. На M1 с 8 ГБ общей памяти модель на
4-8 млрд параметров пришлось бы квантовать до 4 бит, 120 вызовов упирались бы в лимит
30 минут, а воспроизводимость у генеративного ранжирования заметно хуже, чем у
cross-encoder. Выигрыш неочевиден: ошибки, которые остаются после атрибутного слоя, это
в основном категориальные различия, где cross-encoder и так силен.

**Только bi-encoder, без cross-encoder.** Быстрее в разы. По P@1 cross-encoder сам по себе
даже слегка проигрывает слиянию (0,597 против 0,613). Но он доводит Recall@10 до единицы
и поднимает MRR, а главное - именно поверх него атрибутный слой и слой отрицаний дают свой прирост.
Если его убрать - значит потерять около 5 п.п. итогового P@1, а бюджет времени позволяет его держать.

**Использование структуры "три кандидата на декларацию".** В выданных данных 360 регуляций
это ровно 120 троек, и напрашивается глобальное назначение (венгерский алгоритм) с
ограничением "каждая тройка достается одной декларации". Отклонено осознанно: это подгонка
под конкретный датасет, на скрытом тестовом наборе структура может быть другой, и решение
сломается. Венгерский матчинг оставлен только как диагностика.

**Готовый `rank_bm25`.** Лишняя зависимость ради всего 40 строк на numpy.

## Допущения

Задание не фиксирует ряд условий, поэтому:

1. **Метрика.** Явно не названа. Считаем, что на каждую декларацию приходится одна верная
   регуляция, поэтому целевые метрики - P@1 и MRR@10, а Recall@10 вспомогательный.
2. **Поле `notes`.** Общее для всей товарной группы и обрезано на полуслове; в нем часто
   текст про соседние позиции (в регуляции про двигатели половина `notes` - про подшипники
   и кондиционеры). В индекс не идет.
3. **Служебные поля.** `G221` (валюта), `G34` (страна), `G42` (стоимость),
   `has_acceptance_docs` считаем шумом относительно кода ТН ВЭД. `desc_extention` и
   `permitting_docs` используются: именно там лежат решающие атрибуты.
4. **Направление `ИМ`/`ЭК`.** Влияет на применимость мер, но не на классификационный код,
   поэтому кандидатов по нему не фильтруем.
5. **Потерянные надстрочные степени `см?`.** Восстанавливаются как `см3`, `г/м?` как `г/м2` - по смыслу контекста.

## Компромиссы

- **Длина контекста реранкера 384 токена.** Описание с раскрытыми ссылками и пояснением
  почти всегда укладывается; редкие длинные `explanation` обрезаются. Обмен качества на
  время в рамках 30-минутного лимита.
- **Атрибутный слой покрывает числовые пороги и отрицания, но не категориальные признаки**
  (мороженое/охлажденное, б/у/новое, трикотаж/ткань). Категориальные различия оставлены
  cross-encoder-у: список таких признаков открытый, и правила под них плохо переносятся
  на скрытый тестовый набор. Отрицания вынесены в отдельный слой именно потому, что там
  правило одно и грамматическое, а не список признаков.
- **Веса ступеней подобраны на 62 размеченных примерах.** Выбирались не по максимуму сетки,
  а по середине плато. Устойчивый блок - приор 2,0-2,5 при весе атрибутов 1,0-1,5 и
  практически любом весе отрицаний, взяты 2,5 / 1,0 / 0,5. Отдельные точки сетки давали
  и 0,790, но это одиночные пики на 62 примерах. Вес отрицаний выше 0,6 или
  вес атрибутов выше 2,0 качество ухудшают: начинают весить ложные срабатывания вроде
  "текстильное армирование отсутствует", где в область отрицания попадает и слово
  "армирование", общее для всех кандидатов.
- **Приор от порядка слияния: убран, потом возвращен.** Сначала он добавлялся слабым весом
  как средство разведения ничьих. На первых 32 размеченных примерах он не менял ни P@1,
  ни MRR ни при одном весе, и был убран. Однако, после расширения разметки до 62
  примеров оказалось, что при весе около 2,5 он дает +6,4 п.п. P@1 - это самый большой
  единичный вклад после атрибутного слоя.
- **Стеммер усекающий, а не морфологический.** `pymorphy` дал бы точнее, но это лишняя
  зависимость и словари в офлайне.

## Валидация

Разметки в задании нет. Вручную размечено 62 декларации из 120 (`dev/dev_labels.jsonl`),
для каждой зафиксирован верный `regulation_id` и обоснование выбора. Это позволяет мерить
изменения, а не полагаться на ощущения.

Размер выборки пришлось наращивать по ходу работы, и это себя оправдало. На первых 32
примерах итоговая конфигурация показывала P@1 = 0,781, на 62 та же конфигурация дала 0,677:
первая половина оказалась заметно легче. Именно расширение разметки вскрыло, что приор
от порядка слияния - не мертвый код, а существенный источник сигнала. Отсюда практический
вывод: на выборке в 30 примеров разница в один-два случая неотличима от шума, и решения
о полезности компонента принимать по ней нельзя.

## Структура

```
run.py                   точка входа
download_models.py       скачивание моделей, вне лимита запуска
prepare_env.sh           установка окружения
src/normalize.py         нормализация текста
src/io_utils.py          чтение данных, запись и валидация CSV
src/lexical.py           BM25 на numpy
src/dense.py             эмбеддинги bge-m3
src/rerank.py            cross-encoder
src/attributes.py        числовые пороги и измерения
src/negation.py          полярность признаков и противоречия
src/tnved_tree.py        разбор справочника, раскрытие ссылок
src/pipeline.py          сборка ступеней
dev/dev_labels.jsonl     ручная разметка 62 деклараций
dev/evaluate.py          P@1, MRR@10, Recall@10
dev/selftest.py          проверки формата и правил, без моделей
notes/error_analysis.md  разбор пяти ошибок
```

Каталоги `models/` и `.venv/` в репозиторий не входят - воспроизводятся через
`prepare_env.sh`. `data/` содержит выданные входные файлы.

## Версии

Python 3.10+ (проверялось на 3.11), зависимости зафиксированы в `requirements.txt`.

| Модель | Параметров | Ревизия |
|---|---|---|
| `BAAI/bge-m3` | 568 млн | `5617a9f61b028005a4858fdac845db406aefb181` |
| `BAAI/bge-reranker-v2-m3` | 568 млн | `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e` |

Обе сильно ниже лимита в 8 млрд параметров. Ревизии закреплены в `download_models.py`:
без этого тег `main` со временем уедет и результат перестанет воспроизводиться.
Модели выкачиваются в `./models` и грузятся оттуда офлайн.
